# 2026-10-03 · 作品来源分类字段分析 · wsnxxxs

- 负责人：wsnxxxs｜执行 AI：Codex｜范围：仅分析，不实施字段删除。

## 本轮目标

分析共池后是否可以去掉数据包 / 投稿的来源分类字段，以及当前依赖与删除边界。

## 发现与建议

- 实际有多组标记：后端 catalog / library 构造 `curated`，adminWork 派生 `source=curated|upload`；前端 uploadResult 加 `upload`，mergePlatform 维护 `t.curated` 底册再合并 API 作品。当前 works 表没有对应的独立分类列。
- 建议从业务作品对象和前端接口中移除分类，以统一结构承载完整作品目录，统计、展示与资格读取同一作品列表。两个物理加载入口可保留；内部存储适配不作为作品身份暴露。
- 不能裸删：Gallery 的媒体 URL、三维沙盘 / 展厅、iframe / fold、审核按钮和 ID 键依赖这些字段；后端的开关 / 校准写入位置、内容审批和覆盖记录也仍有分支。分别改为统一资源地址、是否有预览资源、实际操作权限、审核状态及 task/id 键。
- 不是新增 storageType 对外替代旧 source；来源分流应限于内部加载 / 存储逻辑。无需为消除业务分类搬迁全部资源或把私有包塞进数据库。
- Harness、官方 / 非官方服务商、作者 / 所有者、生成信息、审核状态保留。历史 curated_as 防重复收录、votes.source 区分投票业务，以及历史投票身份快照不随本轮分类分析删除或改写。
- 上轮「3 件 / 5 件」是执行者只数了一个入口的口径错误，当前页面总数正确，不据此声称现有计数代码有错误。
